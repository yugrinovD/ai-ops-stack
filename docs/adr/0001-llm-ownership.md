# ADR 0001: общий Ollama и владение LLM-интеграцией

- Статус: принято
- Дата: 2026-11-21
- Контекст: `gogate`, `lmlog`, `ops-console`

## Контекст

`lmlog` и `gogate` исторически умели поднимать собственный Ollama и ходить в
него напрямую. Это давало два контейнера, два volume с моделями, два `ollama
pull` и дублирование retry/таймаутов/метрик. `ops-console` при этом вообще не
должен знать про Ollama.

## Решение

1. **Ollama — общая внешняя инфраструктура.** В полном стеке её поднимает
   `infra/docker-compose.yml`; порт `11434` не публикуется наружу.
2. **`gogate` — единственный владелец LLM-интеграции.** Провайдеры, таймауты,
   retry, fallback, rate limit, кэш, метрики, стоимость и audit живут в
   `gogate`.
3. **`lmlog` — consumer.** По умолчанию (`LMLOG_LLM_MODE=gateway`) он вызывает
   `gogate` по OpenAI-совместимому API. Прямой Ollama остаётся только в
   standalone-режиме `direct`.
4. **`ops-console` не знает про Ollama.** Он использует только `gogate` и
   `lmlog`.
5. **Standalone-профили `ai`** в `gogate` и `lmlog` — dev-удобство, а не
   владение. Они взаимоисключающие с полным стеком.

## Последствия

- Один Ollama-контейнер, один volume, один pull в полном стеке.
- Все LLM-вызовы проходят через один шлюз: лимиты, стоимость, трейсы и кэш
  видны в одном месте.
- При падении `gogate` или Ollama `lmlog` деградирует до детерминированной
  эвристики; ingest/scan/trends не падают.
- Появляется сетевая зависимость `lmlog → gogate`; она осознанная и
  компенсируется fallback-ом.
- Для standalone-разработки нужно явно выбрать `LMLOG_LLM_MODE=direct` и не
  запускать её одновременно с `infra/`.

## Альтернативы

- **Оставить Ollama в каждом репозитории.** Отклонено: два контейнера, два
  volume, дублирование логики и конфликт порта.
- **Дать `lmlog` собственный LLM-слой.** Отклонено: размывает границы и
  дублирует retry/лимиты/метрики.
- **Заставить `ops-console` ходить в Ollama.** Отклонено: консоль не должна
  знать про LLM-инфраструктуру.
